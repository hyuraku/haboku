# ADR-0005: 新規ノートのファイル名のために chrono を足す

- 日付: 2026-08-09
- ステータス: 採用

## 文脈

<!-- どんな問題・制約の中で決めたか。評価軸の優先度を先に書く（総合点方式の罠を避ける） -->

`Cmd+N` の新規ノートは時刻ファイル名（`2026-08-09-153301.md`）にする（`docs/spec.md`）。
**std にローカル時刻を得る手段が無い。** `SystemTime` は UNIX epoch からの経過時間しか持たず、
暦への変換もタイムゾーンの適用も自前になる。

前身（gpui 版）は `chrono::Local` を使い、その採用理由を
「gpui-component の依存に既に入っているので追加ダウンロードは発生しない」と書き残していた。
**この理由は iced では成立しない。** 前身の判断をそのまま持ってくると、根拠が消えたまま依存だけが残る。

評価軸の優先度:

1. **ファイル名が壁時計と一致すること**。JST の 00:30 に作ったノートが前日の名前になるのは事故
2. 依存を増やさないこと
3. 実装量が小さいこと

## 決定

<!-- 何を選んだか1〜3行 -->

**`chrono` を直接依存に足す**（`default-features = false, features = ["clock", "std"]`）。
用途は `chrono::Local::now().format("%Y-%m-%d-%H%M%S")` の 1 箇所だけ。

## 却下した代替案

<!-- 何を・なぜ見送ったか。「なぜこれでないのか」が将来いちばん効く記録 -->

- **既に依存ツリーにある `time` 0.3 を使う**。追加ダウンロードが無いので最初の候補だった。
  却下したのは、**`local-offset` はマルチスレッドプログラムで `IndeterminateOffset` を返す**ため。
  健全性のための意図的な設計で、iced（wgpu・tokio）は確実にマルチスレッド。
  つまり「動くように見えて実行時に必ず失敗する」選択肢だった
- **UTC で名前を付ける**（std だけで完結する）。JST では 9 時間ずれ、日付が変わる時間帯に作ると
  前日の名前になる。優先度 1 に反する
- **暦計算とタイムゾーン解決を自前で書く**。暦（civil_from_days）は 15 行ほどで書けるが、
  タイムゾーンは `/etc/localtime` の解析か `localtime_r` の呼び出しが要る。
  **ファイル名のために持つには重い**し、DST を含めて自前で正しく保つ気はない
- **時刻をやめて連番にする**（`untitled-2.md`）。依存はゼロになるが、
  `docs/spec.md` の仕様変更になる。今そこを変える理由が無い

## 帰結

<!-- この決定で背負うトレードオフ。非標準技術なら innovation token の消費として明記 -->

- 依存が 2 つ増える（`chrono` と `iana-time-zone`）。**前身と違い、今回は追加ダウンロードが発生する**
- `default-features` を切っているので `serde`・`oldtime` などは入らない
- **用途が 1 箇所しかない**ので、将来 std にローカル時刻が入るか、
  ファイル名の仕様が変われば剥がせる。剥がしやすさを保つため、
  呼び出しは `create_note()` の 1 行に閉じてある

## 学び

**継承した判断は、根拠ごと継承されているか確かめる。** 前身の「追加ダウンロードが発生しない」は
当時は正しかったが、土台を替えた時点で嘘になっていた。コメントに理由が書いてあったから気づけた
（理由の無いコードだったら、そのまま持ってきて依存だけ増やしていた）。
