# ADR-0010: ⌘ 付きの打鍵を本文にも入力欄にも入れない

- 日付: 2026-08-11
- ステータス: 採用
- 関連: ADR-0004（同じ制約の続き。あちらは `text_input`、こちらは `text_editor` と実害の方）

## 文脈

<!-- どんな問題・制約の中で決めたか。評価軸の優先度を先に書く（総合点方式の罠を避ける） -->

アプリの起動確認中に `Cmd+P` を押したところ、パレットが開くと同時に**エディタ本文へ "p" が
挿入され、自動保存で実 vault のノートに書き込まれた**（`git restore` で復元）。

原因は ADR-0004 が記録した制約そのものだが、**見ていた出口が違った**。ADR-0004 は
「subscription はイベントを観測できても消費できない」を `text_input`（パレットを開いたまま
再度 `Cmd+P` を押すと検索欄に "p" が入る）でだけ確かめ、それを理由にトグルをやめた。
実際には同じイベントが `text_editor` にも届く。そしてこちらには**自動保存が付いている**。

iced 側にガードは無い。`iced_widget-0.14.2` の `text_editor.rs` の `Binding::from_key_press`
は `c` / `x` / `v` / `a` だけを `command()` 付きで特別扱いし、それ以外は `text` があれば
`Insert` を返す。`text_input.rs` の文字挿入も同じで、`command()` を見ていない。
macOS は ⌘ 付きの打鍵にも `text` を載せてくるので、`Cmd+P` / `Cmd+N` / `Cmd+R` の 3 つ全部が該当する。

差し込み口は非対称である:

- `text_editor` … `.key_binding()` で既定の解釈を丸ごと置き換えられる
- `text_input` … 同等の hook が無い。挿入はウィジェット内部で完結する

評価軸の優先度:

1. **ノートを失わないこと。** 打った覚えのない 1 文字が黙ってディスクに残るのは論外
2. 押した結果が予測できること（ADR-0004 の優先度 1 を引き継ぐ）
3. 既存の操作を壊さないこと（コピー・貼り付け・全選択）

## 決定

<!-- 何を選んだか1〜3行 -->

- **エディタは `key_binding` で塞ぐ。** `Binding::from_key_press` に一度委ね、
  結果が `Insert(_)` かつ ⌘ 付きのときだけ `None` を返す
- **入力欄は「⌘ を押している間に来た入力を受け取らない」で塞ぐ。** App が修飾キーの状態を持ち、
  `PaletteQueryChanged` / `RenameChanged` を破棄する。どちらの `text_input` も値は App が
  持っているので、捨てれば次の描画で元に戻る
- **`Unfocused` で修飾キーの状態を解く。** `ModifiersChanged` はフォーカスがある間しか来ない

## 却下した代替案

<!-- 何を・なぜ見送ったか。「なぜこれでないのか」が将来いちばん効く記録 -->

- **⌘ 付きの打鍵を一律に落とす**（`command()` なら `from_key_press` を呼ばず `None`）。
  実装は最短。却下したのは `Copy` / `Cut` / `Paste` / `SelectAll` が `Insert` より先に
  返っているためで、**混入は止まるがコピー・貼り付け・全選択がまとめて死ぬ**。
  メモアプリとして成立しない
- **`p` / `n` / `r` を名指しで弾く**。今の実害はこれで消える。却下したのは、subscription 側に
  ショートカットを足すたびにこちらへの追記が要る**二重管理**になるため。
  忘れた瞬間に同じバグが同じ形で戻る
- **入力欄で「増えた 1 文字がショートカット文字なら捨てる」**。修飾キーの状態を持たずに済む。
  却下したのは手打ちの "p" と区別が付かないため。**"graphql" と打てない検索欄**になる
- **混入した文字を後から削る**（ADR-0004 が既に却下）。挿入とこちらの削除の順序に依存する。
  今回の案が違うのは、**⌘ の keydown が文字キーより必ず先に届く**点で、
  同一イベント内の処理順に依存しないこと
- **`Unfocused` のリセットを入れない**。行数は減る。却下したのは、`Cmd+Tab` で抜けて
  向こうで ⌘ を離すと「離した」通知が来ず、**戻ってきたとき入力欄が黙って無反応になる**ため。
  `Cmd+Tab` はメモアプリを使いながら最も多い操作の 1 つで、しかも失敗が静かすぎる

## 帰結

<!-- この決定で背負うトレードオフ -->

- **⌘ を押しながらの打鍵は、どの入力面でも文字にならない。** 将来 ⌘ 付きで文字を入れたい
  機能を作るなら、この 2 箇所を明示的に例外にする必要がある
- **App が修飾キーの状態を持つようになった。** UI の状態ではなく入力デバイスの状態なので、
  持ち続ける限り「実際のキーと食い違う」余地が残る。食い違いの出口（`Unfocused`）は塞いだが、
  これは**穴を 1 つ塞いだのであって、状態を持たない設計より弱い**ことは変わらない
- `text_input` 側は**根本から塞げていない。** ウィジェットは文字を挿入し、こちらが結果を
  捨てている。iced が `text_input` にも `key_binding` 相当を足したら、そちらへ寄せられる

## 学び

**同じ制約でも、出口ごとに実害が違う。** ADR-0004 は制約を正しく理解し、正しく一般化まで
書いていた（「この制約は `Cmd+P` に限らない」）。それでも本文への混入を見落としたのは、
確かめた出口が入力欄だけで、**そこには自動保存が無かった**から。制約を数えるのではなく、
**その制約が通る経路を数える**（ADR-0007 の「同じ性質の穴は経路ごとに開く」と同じ形）。

**「使えるはず」を実際に叩くまで、使えるかは分からない。** このバグは 1 度アプリを起動して
`Cmd+P` を押しただけで踏んだ。テストは全部通っていて、`cargo clippy` も黙っていた。
