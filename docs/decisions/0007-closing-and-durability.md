# ADR-0007: 終了・削除にも保存ガードを通し、閉じられない状態は 2 段階で逃がす

- 日付: 2026-08-10
- ステータス: 採用
- 関連: ADR-0006（「削除の前に保存する」の却下を**取り消す**）

## 文脈

<!-- どんな問題・制約の中で決めたか。評価軸の優先度を先に書く（総合点方式の罠を避ける） -->

外部レビュー（Codex）にコード全体を読ませたところ、**保存ガードの抜けが 2 つ**見つかった。

`save_now()` は「エディタの内容を破棄してよいか」を返す設計で、ノート切替・新規作成・
リネームにはこのガードが入っていた。しかし:

1. **ウィンドウを閉じる経路にガードが無い。** iced の `exit_on_close_request` は既定が
   `true` で、閉じる要求はアプリに届く前にプロセスを終わらせる。デバウンス（1 秒）の
   途中で `Cmd+W` を打てば、その 1 秒分は**ディスクにもメモリにも残らず消える**
2. **削除の経路にガードが無い。** これは ADR-0006 で意図的にそうした（下記）

同時に、保存層そのものにも穴があった。`save()` は tmp → rename でアトミック性を
謳っていたが、**中身を fsync していなかった**。プロセスが落ちるだけなら OS の
ページキャッシュが救うが、電源断では「新しい名前で中身が空」が起き得る。

評価軸の優先度（ADR-0006 から変えない）:

1. **ノートを失わないこと**
2. 操作の結果が予測できること
3. `.md` が唯一の真実であること

ただし今回は 1 の中に**対立**がある。「本文を守る」ために閉じるのを拒み続けると、
ユーザーの出口は強制終了だけになり、**結局全部失う**。守ったことにならない。

## 決定

<!-- 何を選んだか1〜3行 -->

- **`exit_on_close_request(false)` にして、閉じる要求を自分で処理する。** 保存に成功したら閉じる
- **保存に失敗したときは 2 段階。** 1 回目は閉じずに理由と次に起きることを出す。
  2 回目は本文を `<ファイル名>.rescue` へ退避してから**必ず閉じる**
- **削除も捨てる前に書き戻す**（ADR-0006 の却下を取り消す）
- **`save()` は rename の前に `sync_all()` する。** 一時ファイル名にはプロセス ID を混ぜる
- **外部で書き換えられたファイルの上書き検知は入れない**（下記）

## 却下した代替案

<!-- 何を・なぜ見送ったか。「なぜこれでないのか」が将来いちばん効く記録 -->

- **保存できないなら閉じない（1 段階）**。本文優先で筋は通る。却下したのは、
  **メモ帳で保存が失敗する原因が待っても直らない**ため。容量不足・ドライブが外れた・
  権限が変わった、のどれでも再試行は失敗し続ける。出口は `Cmd+Option+Esc` だけになり、
  それを選んだ瞬間に本文は消える。**閉じ込めても守れていない**
- **保存できなくてもそのまま閉じる（1 段階）**。出口はあるが、切替を中断してまで守った
  本文を最後の一歩で捨てる。守る仕組みの意味が無くなる
- **1 回目からいきなり退避して閉じる**。出口も本文も守れるが、ユーザーは**何が起きたか
  知らないまま**終了する。次に開いたとき `.rescue` を見て初めて気づく。警告を 1 回挟む
- **終了時に確認ダイアログを出す**。素直だが、iced にモーダルの標準ウィジェットが無く、
  閉じる直前に自前の stack を出す経路を作ることになる。ステータス行のエラーで足りる
- **外部変更の検知（保存直前に mtime を照合して、ズレていたら中断）**。他ツールの変更を
  潰さずに済む。却下したのは、**このアプリが「既存の repo を開くビューア」ではなく
  メモ帳**だから。同じファイルを別のツールが同時に触る前提を置いていない
  （spec の非目標「同期・共有・マルチデバイス。外部変更との衝突解決もしない」と一致）。
  入れるなら `save_now()` 成功後に実 mtime を取り直す連動も要る（いまは `now` を入れており、
  そのままだと次回保存が必ず誤検知する）。
  **再確認（2026-08-11）**: 外部レビュー（Codex）が同じ点を high として再提起したが、
  **却下を維持**した。運用は「`~/Documents/haboku` の `.md` を haboku だけで触る」であり、
  外部エディタ（VS Code・Zed）や別プロセスからの書き込みを想定しない、とユーザーが明示した。
  この前提が崩れる条件は 3 つ（いずれか 1 つでも成立したら入れ直すこと）:
  iCloud Drive の「デスクトップと書類」同期を有効にして別端末からも書く /
  vault を git で `pull` する / haboku を同時に 2 つ起動する
- **親ディレクトリも fsync する**。rename 自体の永続化まで保証できる。却下したのは、
  省いても最悪の結果が「古い内容のまま残る」であって**壊れたファイルではない**ため。
  `save()` が守ると宣言しているのは前者だけ

## 帰結

<!-- この決定で背負うトレードオフ -->

- **保存できない状態で 2 回閉じると、本文は `.rescue` に落ちてアプリは終了する。**
  退避先を伝える経路は stderr しかない（閉じたあとに画面は無い）。Finder から
  見つけてもらう前提で、退避先はノートのディレクトリ → vault ルート → 一時ディレクトリの順に試す
- **`.rescue` を回収する UI はアプリに無い。** `.md` ではないので一覧にも出ない。
  `.trash` と同じく Finder で扱う
- **削除は保存に失敗すると実行されない。** ADR-0006 はこれを嫌って却下していたが、
  `.trash` への退避は同じディレクトリからの rename なので、**保存が権限で失敗する状況では
  削除もどのみち失敗する**。失う機能は無い
- 一時ファイル名が `<name>.md.<pid>.tmp` になった。プロセスが書き込み中に落ちると残る
  （固定名時代と同じ性質で、pid ごとに 1 つ）

## 学び

**却下理由は、書いてあるから後で検証できる。** ADR-0006 は「削除の前に保存する」を
「保存に失敗したときに削除できなくなるほうが困る」という理由で却下していた。今回その理由を
突き合わせたら、`.trash` への退避が同一ディレクトリの rename である以上**成立しない**と分かった。
チャットに置き去りにしていたら、判断そのものが不可視のまま残っていた。

**安全装置は、失敗したときに何が起きるかまで設計する。** 「保存できるまで閉じない」は
一見いちばん安全だが、ユーザーに残る手段（強制終了）まで数えると最悪の結果になる。
ADR-0002 で廃止した読み込み専用モード（「打てるのに保存されない＝書いた本文が消える」）と
**同じ形の罠**で、守る対象ではなく**逃げ道**を見落としていた。

**同じ性質の穴は経路ごとに開く。** `save_now()` のガードは切替・作成・リネームには通してあり、
削除と終了だけが抜けていた。「ガードを作った」ではなく**「エディタを上書き／破棄する経路を
全部数えた」**で確認しないと、数え漏れた経路がそのまま穴になる。
