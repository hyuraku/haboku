# ADR-0014: 保存をワーカーへ出し、ガードの判定を完了メッセージへ移す

- 日付: 2026-08-11
- ステータス: 採用
- 関連: ADR-0012（却下欄に置いた「保存を非同期タスクへ出す」を**採用に転じる**）、ADR-0007

## 文脈

<!-- どんな問題・制約の中で決めたか。評価軸の優先度を先に書く（総合点方式の罠を避ける） -->

`docs/spec.md` の自動保存の行は「**保存できない間も UI が固まらない**」を要求に挙げている。
しかし `save_now()` は `update()` から同期で呼ばれ、その中で
`write` → `sync_all` → `rename` を**完了まで待って**いた。

`sync_all` は OS のキャッシュではなく媒体への到達を待つ呼び出しで、ローカル SSD なら
1ms 未満だが、**iCloud Drive・外付け・ネットワーク共有・劣化したディスク**では
秒単位で返らないことがある。その間 iced は次の描画も打鍵も処理できない。

ADR-0012 のバックオフ（500ms→30s）は**固まる回数**を 1/300 にしたが、
**1 回あたり何秒固まるか**には触れていない。ADR-0012 自身が却下欄にこう書いている:

> **保存を非同期タスクへ出す**… UI が固まる問題の**本筋の解**… 却下したのは、
> `save_now()` の戻り値「エディタの内容を破棄してよいか」が**同期であることに乗っている**ため

外部レビュー（Codex・敵対的レビュー 2 巡目）がこの申し送りを未処置の high として指した。
公開を判定基準に据える以上、**固まる条件を残したまま「固まらない」と書いてある状態**は通せない。

評価軸の優先度（ADR-0007 / ADR-0012 から変えない）:

1. **ノートを失わないこと**
2. 操作の結果が予測できること
3. `.md` が唯一の真実であること

「UI が固まらない」は 1 と 2 の下。**速さのために喪失の可能性を増やす取引はしない。**

## 決定

<!-- 何を選んだか1〜3行 -->

**書き込みを `Task` へ出し、ガードの判定を `Message::Saved` へ移す。** 3 つに割った:

- `begin_save(app, next, autosave_at)` — 書くものが無ければ `next` をその場で実行し、
  あれば `next` を `app.pending` に預けて書き込みだけ投げる
- `Message::Saved(Result<(), String>)` → `finish_save` — 成功なら `notes` を更新して
  `pending` を実行、失敗ならエラーを出して **`pending` を捨てる**
- `PendingAction` — 切替・新規・リネーム・削除・終了の 5 経路。**どれもエディタの内容を
  捨てる操作**で、従来 `if !save_now(app) { return; }` で塞いでいたもの

**ガードの意味論は 1 つも変えていない。判定の場所だけが移った。**

決めたことがもう 3 つある:

- **同時に走らせる保存は 1 本だけ。** 走っている間の要求は `pending` に積むだけ。
  直列なので「古い保存の完了が新しい保存を上書きする」順序事故が**起こり得ない形**になり、
  世代番号を持たずに済む。`notes` を触る操作も全部この後ろに並ぶので、
  控えた `index` が完了時にズレることもない
- **保存中に打たれた分があれば dirty を畳まない。** 書き出すのは投げた瞬間のスナップショット。
  完了時にエディタの中身がそれより新しければ dirty のままにする（畳むと次の切替で消える）
- **バックオフの基準時刻は `InFlight` に持ち回す。** 完了時に `Instant::now()` を読むと、
  `should_save` の境界をテストから組み立てられなくなる（ADR-0012 で得た性質を壊さない）

`tokio` を直接依存に足した。**新しい依存ではない**（iced の `tokio` feature で既に
ツリーにいる）。`spawn_blocking` を名指しで呼ぶために宣言しただけで、`rt` 以外は切ってある。

## 却下した代替案

<!-- 何を・なぜ見送ったか。「なぜこれでないのか」が将来いちばん効く記録 -->

- **自動保存（tick 経由）だけ非同期にし、明示操作は同期のまま。** 差分は小さく、
  ガードの意味論にも触らない。却下したのは**保証の線引きが説明できない**ため。
  「打鍵中は固まらないが、ノートを切り替えると固まる」は、遅い vault では
  切替のたびに数秒止まることを意味する。spec の一行を半分だけ満たしても、
  ユーザーから見れば固まるアプリのまま
- **実装に合わせて spec を下げる**（「ローカル vault 前提の同期保存」と明記）。
  コード変更ゼロで、想定運用（`~/Documents/haboku`）だけ見れば妥当。却下したのは、
  **公開するとその前提が外れる**ため。メモアプリの vault を iCloud Drive や
  Dropbox に置くのはごく普通の使い方で、そこで固まる
- **`Task::future` に `vault::save` を直に置く**（`spawn_blocking` を使わない）。
  依存を足さずに済む。却下したのは、ブロッキング I/O で async のワーカーを占有するため。
  いま保存は 1 本ずつなので実害は出にくいが、**「ここはブロックする」を型と関数名で
  宣言しておくほうが後から読める**
- **世代番号（generation）で完了を突き合わせる。** レビューの推奨案。却下したのは、
  **直列にした時点で突き合わせる相手が 1 つしかない**ため。使われない識別子は
  「並行に走り得る」という誤った読み方を将来の自分に渡す（BSSN）

## 帰結

<!-- この決定で背負うトレードオフ -->

- **`update()` の中で保存が完了しなくなった。** テストは `send()` のあとに
  `flush_saves()` を呼ぶ必要がある。差し替えているのは「どのスレッドで走らせるか」だけで、
  何を書くか（`InFlight`）も完了後の分岐（`finish_save`）も本番と同じ経路を通る
- **保存の遅い環境では、切替が目に見えて遅れる。** 固まらない代わりに「押したのにすぐ
  切り替わらない」が起きる。ADR-0007 の「保存に失敗したら切り替えない」を守る以上、
  待ちそのものは消せない。エラーはステータス行に常駐するので**黙って待つことはない**
- **未保存マーカーが、保存の遅い環境では点きやすくなる。** `DIRTY_MARKER_DELAY`（3 秒）を
  超えて保存が返らなければ点灯する。これは劣化ではなく**正しい表示**（実際まだ書けていない）
- 状態が 2 つ増えた（`saving` / `pending`）。解除点はどちらも `finish_save` の 1 箇所だけ

## 学び

**「大きすぎるから今回は見送る」と書いた判断は、書いた時点では正しくても賞味期限がある。**
ADR-0012 の却下欄は理由まで正確に書けていた（`bool` が同期であることに乗っている）。
それでも未処置の穴であることは変わらず、**公開という判定基準が入った瞬間に評価が反転した**。
却下の記録に理由が残っていたおかげで、今回は文脈を再構成せずに実装へ入れた。

**非同期化の本体は「スレッドを変えること」ではなく「同期の戻り値に乗っていた意味を、
どこへ移すか」だった。** `save_now() -> bool` の `bool` は、実は
「エディタの内容を破棄してよいか」という**許可**を運んでいた。スレッドの話だと思って
着手すると、この許可の行き先を決め忘れてデータ喪失の穴が開く。
