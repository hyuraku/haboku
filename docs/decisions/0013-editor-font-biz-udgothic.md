# ADR-0013: エディタの等幅フォントを `BIZ UDGothic` にする

- 日付: 2026-08-11
- ステータス: 採用
- 関連: ADR-0003（**フォントの選択だけを置き換える**。「総称ファミリを使わず名指しする」という
  ADR-0003 の決定そのものは有効）、ADR-0009（weight 完全一致条件）

## 文脈

<!-- どんな問題・制約の中で決めたか。評価軸の優先度を先に書く（総合点方式の罠を避ける） -->

ADR-0003 追記（2026-08-10）で、`Font::with_name("Osaka-Mono")` が**一度も解決されていなかった**
ことが分かった。`"Osaka-Mono"` は PostScript 名で、fontdb が照合するのはファミリ名だからだ。
Done の定義にある「コードブロックの桁が揃う」は未達のまま、公開判定の宿題として残っていた。

そして「`"Osaka"` に直せば済む」ではない。実測すると:

| ファイル | family (name id 1) | PostScript (id 6) | usWeightClass |
| --- | --- | --- | --- |
| `Osaka.ttf` | `Osaka` | `Osaka` | 400 |
| `OsakaMono.ttf` | `Osaka` | `Osaka-Mono` | 400 |

**比例と等幅がファミリ名・weight・幅クラスまで完全に同じ。** fontdb の照合はファミリ名 +
weight + style + stretch なので、この 2 face は**問い合わせ側から区別できない**。
どちらが返るかはディレクトリの走査順に依存する。名前で選び分けられないものを名指ししても、
それは指定ではなく賭けにしかならない。

評価軸の優先度（ADR-0003 から変えない）:

1. **漢字が 1 文字も消えないこと**
2. コードブロックの桁が揃うこと（等幅であること）
3. 追加の依存・配布物を増やさないこと（フォントを同梱しない）

## 決定

<!-- 何を選んだか1〜3行 -->

**`Font::with_name("BIZ UDGothic")` を名指しする。**

選定理由は 3 つとも `cmap` / `hmtx` / `OS/2` / `name` を直接読んで確認した（目視の印象ではなく数字）:

- **ファミリ名が一意**。比例版は `BIZ UDPGothic` という**別ファミリ**なので、`Osaka` の
  同居問題が構造的に起きない
- **Regular が `usWeightClass = 400` ちょうど**。cosmic-text は `font_weight_diff == 0` の
  face しか名指しファミリから採らない（ADR-0009）ので、既定の `Normal` で当たる
- **ASCII が 1024、漢字・かな・約物が 2048**（upem 2048）。ASCII 内は全部同じ幅で、
  CJK はその**ちょうど 2 倍**。等幅の定義を満たす

macOS の downloadable font asset（`/System/Library/AssetsV2/com_apple_MobileAsset_Font*`）
として同梱されており、fontdb 0.23 はこのディレクトリを走査する。同梱物は増えない。

## 却下した代替案

<!-- 何を・なぜ見送ったか。「なぜこれでないのか」が将来いちばん効く記録 -->

- **`Font::with_name("Osaka")` に直す**。1 文字の修正で済むが、上表のとおり等幅 face を
  選べる保証がない。**「たいてい当たる」を「指定した」と呼ばない**
- **fontdb / cosmic-text 側で face を直接選ぶ**（PostScript 名で引く）。技術的には可能だが、
  iced の `Font` は family / weight / stretch / style しか持たないので、iced のフォント解決を
  迂回する層を自分で持つことになる。**1 つのフォントを選ぶために払う額ではない**
- **`OsakaMono.ttf` を読み込んで name テーブルを書き換え、別ファミリ名として登録する**。
  同梱せずに Osaka Mono を確実に選べる唯一の方法。却下したのは、システムフォントのパスが
  macOS のバージョンで動くうえ、**フォントバイナリを実行時に書き換える**という説明しづらい
  仕掛けが 1 つ増えるため（innovation token を払う価値が無い）
- **等幅 CJK フォント（HackGen・PlemolJP・UDEV Gothic 等）を同梱する**。`0` と `O`、`1` と `l`
  の判別は最も良くなる。却下したのは配布物に数 MB とライセンス表記を抱えるため。
  **標準搭載で要求 2 を満たせるうちは払わない**（ADR-0003 と同じ判断）
- **`Hiragino Sans` / `Yu Gothic` / `Klee`**。どれも日本語は全角固定だが、**ASCII が比例**
  （実測: Yu Gothic は `i` が 266、`W` が 930）。桁が揃わないので要求 2 を満たさない

## 帰結

<!-- この決定で背負うトレードオフ -->

- **UD ゴシックはコーディングフォントではない。** `0` にスラッシュが無く、`1` `l` `I` の
  区別も強くない。メモアプリのコードブロックを読む用途では許容範囲だが、
  ここが不満になったら同梱案（却下欄の 4 つ目）へ進む
- **`BIZ UDGothic` が入っていない macOS では静かにフォールバックする。** ADR-0003 の
  帰結と同じ性質で、漢字は出るが等幅でなくなる方向の劣化。ただし **Osaka と違って
  「入っているのに選べない」ことは起きない**
- ADR-0003 の「実データで桁が揃うことを確認済み」という主張は、この ADR の実測で初めて
  裏が取れた。**ADR-0003 追記の宿題はここで閉じる**

## 学び

**名指しできるかどうかは、フォントの側の都合で決まる。** `Osaka` は「名前が間違っていた」の
ではなく、**正しい名前を書いても目的の face に到達できない**構造だった。名指しという手段が
成立するかを先に確かめずに、名前の綴りだけを疑っていた。

**フォントの検証はレンダリング結果ではなくテーブルで始めたほうが速い。** 画面を見て
「等幅っぽい」を判定するより、`hmtx` の advance を 7 文字分並べるほうが確実で、
しかも候補フォントを一気に比較できる（実際 4 ファミリの可否が 1 コマンドで割れた）。
