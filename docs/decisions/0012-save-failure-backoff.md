# ADR-0012: 保存が失敗し続ける間はバックオフする。退避に失敗したら閉じない

- 日付: 2026-08-11
- ステータス: 採用
- 関連: ADR-0007（「2 回目は必ず閉じる」を**部分的に取り消す**）

## 文脈

<!-- どんな問題・制約の中で決めたか。評価軸の優先度を先に書く（総合点方式の罠を避ける） -->

外部レビュー（Codex・敵対的レビュー）で、保存の**失敗経路**に 2 つの穴が見つかった。
どちらも「安全装置が、失敗したときに何が起きるかまで設計されていない」形（ADR-0002 / ADR-0007 と同型）。

**1. 失敗した保存を 10Hz で再試行し続ける。** 保存が失敗すると `save_now()` は
`dirty_since` も `last_edit` も更新しない。つまり `should_save()` の 2 本の条件は
以後**永久に真**で、100ms の tick ごとに UI スレッドで
「一時ファイル作成 → 書き込み → `sync_all`」を回し続ける。
遅い / 切断された / 容量ゼロの vault では**画面が固まる**。そして固まると、
最後の手段として用意した「本文を選択してコピーで逃がす」すらできなくなる。

**2. 退避に失敗しても閉じる。** ADR-0007 は 2 段階の終了を決め、2 回目は
「`.rescue` へ退避してから**必ず閉じる**」とした。しかし実装は
`write_rescue()` の戻り値を `eprintln!` するだけで、**失敗しても `window::close` を返す**。
容量ゼロなどで通常保存も退避先も全滅したとき、唯一残っていたメモリ上の本文を
**行き先が 1 つも無いまま捨てる**。ADR-0007 が守ろうとしたものが、
ADR-0007 の実装で消える経路になっていた。

評価軸の優先度（ADR-0007 から変えない）:

1. **ノートを失わないこと**
2. 操作の結果が予測できること
3. `.md` が唯一の真実であること

## 決定

<!-- 何を選んだか1〜3行 -->

- **自動保存の失敗には指数バックオフを掛ける。** 500ms から倍々、上限 30 秒。
  判定は `should_save()` に `retry_after` を AND で足す（純粋関数のまま境界をテストできる）
- **数えるのは自動保存の失敗だけ。** 切替・作成・終了などユーザーの操作は**明示的な再試行**
  とみなして待たせない。保存が通れば `clear_dirty()` がバックオフごと畳む
- **退避に失敗したら閉じない。** 本文をエディタに残し、理由と自力退避の手段
  （選択してコピー）をステータス行に常駐させる。空きを作ってもう一度閉じれば退避は通る

## 却下した代替案

<!-- 何を・なぜ見送ったか。「なぜこれでないのか」が将来いちばん効く記録 -->

- **保存を非同期タスクへ出す**（`Task::perform` でスレッドへ逃がす）。
  UI が固まる問題の**本筋の解**で、遅い vault では成功時にも効く。却下したのは、
  `save_now()` の戻り値「エディタの内容を破棄してよいか」が**同期であることに乗っている**ため。
  非同期にすると切替・削除・終了のガードが全部「保存の完了を待つ状態」を持つことになり、
  今回の 1 件の修正としては大きすぎる。**バックオフは固まる頻度を 1/300 にするが、
  1 回あたりの同期 I/O は残る**（申し送り: `docs/implementation-notes.md`）
- **失敗したら自動保存を止めて、ユーザーの明示操作だけで再試行する。** 実装は最も単純。
  却下したのは、**原因が直ったことに自動では気づけない**ため。外付けドライブを挿し直す・
  容量を空けるといった復帰は普通に起きる（実際に ADR-0007 のテストが
  「権限を戻したら保存が通る」を固定している）
- **一定間隔（例: 5 秒）で再試行する。** 単純だが、直後の復帰に遅く、長期の障害には
  頻繁すぎる。倍々なら両端を同時に満たせる
- **退避に失敗したら、それでも閉じる**（ADR-0007 の現状）。出口は確実にある。
  却下したのは、**その出口が本文を捨てることでしか成立しない**ため。
  「閉じ込めても守れていない」（ADR-0007 の学び）の裏返しで、
  **逃がしても、逃がす先が無ければ守れていない**
- **退避に失敗したら確認ダイアログを出す**。iced にモーダルの標準ウィジェットが無く、
  終了直前に自前の stack を出す経路が要る。ステータス行のエラーで足りる（ADR-0007 と同じ理由）

## 帰結

<!-- この決定で背負うトレードオフ -->

- **保存できない状態が続くと、最大 30 秒書かれない。** 直った直後の 1 回目の保存が
  最悪 30 秒遅れる。未保存マーカー（`DIRTY_MARKER_DELAY`）は出たままなので、
  「まだ書けていない」ことは画面から消えない
- **通常保存も退避も全滅すると、アプリを閉じられなくなる。** 残る出口は強制終了で、
  それを選ぶと本文は失われる。ADR-0007 が「閉じ込めない」と決めた性質を、
  **退避が全滅したときに限って**手放している。本文の行き先が 1 つも無い状態では
  「閉じられる」より「本文が画面に残っている」ほうが価値が高いという判断
- 状態が 2 つ増えた（`save_failures` / `retry_after`）。解除点は `clear_dirty()` の 1 箇所だけ

## 学び

**失敗経路は、失敗が「続く」ことまで設計する。** 1 回の失敗（エラーを出す・遷移を止める）は
テストで固定していたのに、**失敗が繰り返されたときに何が起きるか**は誰も見ていなかった。
`should_save()` の 2 本の条件が失敗時に永久に真になることは、コードを読めば分かる形で書いてあった。

**最後の手段には、最後の手段が失敗したときの設計が要る。** `.rescue` への退避は
ADR-0007 が用意した最後の砦だが、その砦が落ちたときの分岐が無かった。
「安全装置は、失敗したときに何が起きるかまで設計する」を**安全装置自身に適用していなかった**。

**外部レビューは同じ穴を別の角度から見せる。** 3 件（権限・バックオフ・退避失敗）とも
「守る対象は正しく選んだが、守る手段の副作用と失敗を数えていない」という同じ形だった。
