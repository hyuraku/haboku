# ADR-0018: パレットは本文も探す。索引は持たず、本文は連続一致にする

- 日付: 2026-08-15
- ステータス: 採用
- 関連: ADR-0004（パレットの閉じ方）/ 2026-08-11 の公開可否レビュー（`docs/review-2026-08-11-release-readiness.md:62-65, 85`）

## 文脈

<!-- どんな問題・制約の中で決めたか。評価軸の優先度を先に書く -->

**検索がタイトルしか見ていなかった。** `refilter` は `note.title` だけを `match_query` に通し、
全ノートの `raw` は起動時からメモリにあるのに一度も使われていなかった。

これは spec の書きぶりと食い違っていた。非目標にはこうあった:

> **全文検索**（SQLite FTS5 / tantivy）。約 1200 件を 30ms で読めているので、**当面は素の走査で足りる**

却下しているのはインデックス方式であって本文検索そのものではない。にもかかわらず、
その「素の走査」が実装されていない。**非目標の理由付けが、存在しない代替手段を前提にしていた。**
2026-08-11 の公開可否レビューはここを「他人が最初に詰まるのは確実にここ」と判定し、
「非目標を再決定するか、引き受けるか」を保留にした。今回その保留を解く。

判断に効いた事実を先に測った:

| 事実 | 出どころ |
|---|---|
| `match_query` は**飛び飛びの部分列一致**。21 万文字の本文はほぼ全ての文字を含む | `fuzzy.rs:3-7` |
| スコアの長さペナルティ `score -= chars.len() / 8` は 21 万文字で **-26,570**。他のボーナス（最大数十点）が埋もれる | `fuzzy.rs:80` |
| `fold()` は 1 文字あたり 24 バイトを確保する。本文全体に掛けると毎打鍵 30MB 級 | `Range<usize>` 16 + `char` 4 + パディング |
| 前身の Boostnote legacy も本文にはファジーを使わず部分一致だった | `docs/research-2026-08-15-boostnote-legacy-comparison.md:60` |
| `truncate(PALETTE_MAX_RESULTS)` は**ソートの後**にあり、走査コストを削っていなかった | 当時の `refilter` |

## 決定

**本文も探す。索引は作らない。本文は連続一致にする。**

- **タイトル = 部分列一致（従来どおり）／本文 = 連続一致（新規）。** 正規化規則は共有する
  （全角半角・かなカナ・半角カナ濁点。`folded()` が唯一の実装）
- **タイトル一致を先に全部出し、余った枠にだけ本文一致を足す。** 1 本のスコアに混ぜない
- **本文群にスコアを作らない。** 一覧と同じ順（更新の新しい順）に並べる
- **打ち切りを走査の前に効かせる。** タイトルだけで 50 件埋まったら本文は 1 バイトも読まない
- **2 文字未満のクエリでは本文を探さない**（`BODY_MIN_QUERY_CHARS`）
- 走査対象は **`raw` 全体**（frontmatter を含む）
- パレットの 2 行目は、本文に当たった行だけ「フォルダ · タグ」から抜粋に差し替える
- 性能予算は**打鍵 1 回の `refilter` が平均 8ms 未満**。`measure_refilter_with_synthetic_vault` で固定

## 却下した案

- **本文にもファジー（部分列）を使う。** 2 つの理由が独立に致命的だった。(a) 21 万文字の本文は
  ほぼ全ての文字を含むので任意のクエリが当たり、フィルタとして機能しない。(b) 長さペナルティが
  スコアを「ノートの長さ」の指標に変えてしまい、長いノートが常に最下位になる。片方だけ直しても使えない
- **スペース区切りの AND**（前身と同じ形）。今「2 語で絞りたい」という要求が出ていない。
  語ごとにヒットが散るので抜粋をどこから切るかの判断も要る。**復帰条件**: 1 語で絞れない場面が
  実際に出たら、このADRに追記して足す
- **FTS5 / tantivy による索引。** 真実を `.md` の外に置かない、という `vault.rs` の線引きと衝突する。
  そして走査で予算に収まっている
- **正規化済み本文をキャッシュする。** 走査は速くなるがコーパスをもう 1 部メモリに持つことになり、
  無効化の口が保存・リネーム・削除の 3 つに開く。索引を持たない方針とも衝突する
- **本文にスコアを付けて 1 本のランキングに混ぜる。** 重み（行頭からの距離・出現回数など）の根拠に
  なる実データが無い状態で決めるのは占い。タイトルと本文はそもそも別種の証拠

## 帰結

<!-- 決定によって何が起きるか。良いことだけでなく、引き受けた不利益も書く -->

- **frontmatter も検索対象になる。** `tags:` や `date:` の行に当たる。ただし抜粋にその行が出るので、
  なぜ当たったかは画面で説明される。副作用としてタグ検索が一部効く
- **未保存の編集は本文検索に載らない。** `note.raw` は最後に保存された内容で、自動保存が
  最大 2.5 秒で追いつく
- **古いノートの本文ヒットが 50 枠から漏れることがある。** 本文群は更新の新しい順に先着で埋まる
- **1 文字での本文検索はできない。** 単漢字（`鬱` など）1 文字では本文を探さない
- パレットの本文ヒット行ではフォルダ名とタグが見えない（抜粋を優先した）
- **打鍵の予算をこのリポジトリで初めて定義した。** これまで数字があったのは `view()` の 1ms だけで、
  `update()` 側には無かった

### 予算を外したときの最適化ラダー

実装時に 20ms → 7.1ms まで 4 段使った（詳細は `implementation-notes.md`）。**先回りで書かず、
外したら計測してから 1 段ずつ上がる。** まだ使っていない段:

1. 先頭文字の逆像（`か` なら `{か, カ, ｶ}`）を使ったバイト単位のスキップ
2. 増分絞り込み（クエリが伸びた打鍵では前回の候補集合だけ再走査。連続一致は単調なので正しい）
