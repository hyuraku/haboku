各章は 1 つの原理でできている。**原理 → 実際に起きたこと → 一般形 → 次に問うこと**の順に読む。

## 第 1 章 安全装置は、作動したときに何が起きるかまで設計する

**このプロジェクトで最も回数の多い学び。同じ形の事故が 7 回、別の顔をして出た。**

### 実際に起きたこと

| # | 安全装置 | 守るつもりだったもの | 実際に起きたこと | 出典 |
|---|---|---|---|---|
| 1 | 読み込み専用モード | 借り物 vault のデータ | **打てるのに保存されない** ＝ 書いた本文がディスクにもメモリにも残らず消える | [ADR-0002](decisions/0002-drop-read-only-mode.md) |
| 2 | 保存できるまで閉じない | 未保存の本文 | 出口が強制終了だけになり、**それを選んだ瞬間に全部失う** | [ADR-0007](decisions/0007-closing-and-durability.md) |
| 3 | `.rescue` 退避（最後の砦） | 通常保存が全滅したときの本文 | **退避に失敗しても閉じて**、唯一残っていた本文を行き先ゼロで捨てる | [ADR-0012](decisions/0012-save-failure-backoff.md) |
| 4 | 失敗した保存の再試行 | 保存の確実性 | 10Hz で UI スレッドを止め続け、**最後の手段（選択してコピー）すら奪う** | [ADR-0012](decisions/0012-save-failure-backoff.md) |
| 5 | tmp → rename のアトミック保存 | 壊れたファイルを残さない | inode ごと差し替わるので **`0600` のノートが打鍵 1 回で `0644` に緩む** | [ADR-0011](decisions/0011-save-preserves-permissions.md) |
| 6 | 既定パスを黙って作って開く | 初回体験の簡単さ | TCC を拒否されると **空の vault が開く**（＝ 1 の再演） | [ADR-0015](decisions/0015-vault-location-setup.md) |
| 7 | `panic = "abort"`（容量削減） | — | 保存タスクのパニックが `JoinError` として**保存エラー処理そのもの**なので、「本文を残す」が「即死して本文が消える」に化ける | [ADR-0020](decisions/0020-release-profile.md) |
| 8 | ウェルカム画面 | — | ノート未選択でも打てるが `mark_edited` が dirty を立てない ＝ **1 の同型がまだ残っていた** | [公開可否レビュー §3-1](review-2026-08-17-public-release.md) |

### 一般形

**「何を守るか」を決めるのは設計の半分でしかない。残りの半分は「守り方が失敗したときの経路」。**

特に 2 と 3 は対になっている。ADR-0007 が出した「**閉じ込めても守れていない**」と、
ADR-0012 が出した「**逃がしても、逃がす先が無ければ守れていない**」は同じコインの裏表で、
安全装置を足すたびに両方を確かめる必要がある。

そして 1 の解き方が最良の型だった。**機能を足して安全にしようとせず、経路そのものを引き算で消した。**
概念が 1 つ減り、環境変数・分岐・エラー文言・ステータス表示がまとめて消えて、
「開いたものは書ける」の一言で説明できるようになった。

### 次に問うこと

安全装置を設計するとき、以下を順に通す。

1. **作動したとき、ユーザーがいま書いている本文はどこへ行くか**
2. **作動し「続けた」とき何が起きるか**（1 回の失敗ではなく、失敗が繰り返される状態）
3. **安全装置自身が失敗したときの分岐はあるか**（最後の砦にも、砦が落ちたときの設計が要る）
4. **ユーザーに残る最後の手段まで数えたか**（強制終了・電源断・アプリを消す）
5. **その守り方は別の軸で何を削っているか**（権限・属性・応答性・可搬性）
6. **足すのではなく、経路を消して解けないか**

## 第 2 章 穴は経路ごとに開く。塞ぐのは経路ではなく合流点

**「ガードを作った」は完了条件ではない。「その性質が通る経路を全部数えた」が完了条件。**

### 実際に起きたこと

- **`save_now()` のガードが 2 経路で抜けていた。** 切替・作成・リネームには通してあり、
  **削除と終了だけが抜けていた**。外部レビューで最も重い 1 件になったが、
  中身は「既にある仕組みの数え漏らし」だった（[ADR-0007](decisions/0007-closing-and-durability.md)）
- **一般化まで書いてあったのに、出口を数えていなかった。** ADR-0004 は
  「この制約は `Cmd+P` に限らない」と正しく一般化して書いていた。それでも本文への混入を見落としたのは、
  確かめた出口が `text_input` だけで、**`text_editor` には自動保存が付いていた**から。
  実 vault のノートに `p` が書き込まれた（[ADR-0010](decisions/0010-command-key-leak.md)）
- **経路ごとに実装がバラついていた。** リネーム欄を畳む処理は、`DeleteNote` は両方畳み、
  `NewNote` はパレットだけ畳み、`NoteSelected` はどちらも畳んでいなかった。
  結果、開いたままのオーバーレイが別のノートを指し、**Enter で別ノートが前の名前にリネームされる**
- **本文差し替えの経路が 4 つあった。** 起動・セットアップ完了・切替・削除。
  1 つでも漏らすと、切替後の `Cmd+Z` が**前のノートの本文を今のノートへ書き込む**
  （[ADR-0017](decisions/0017-undo-redo.md)）
- **派生状態を片方だけ更新するコードが書けてしまった。** `notes` から導かれる `folders` と `visible` が
  別々に更新されていて、作ったノートがフォルダ件数に反映されなかった

### 一般形

数え上げたら、**経路ごとに塞がず合流点に置く**。これが「今の穴を塞ぐ」と
「次の穴を構造的に防ぐ」の分かれ目になる。

| 性質 | 経路の数 | 置いた合流点 |
|---|---|---|
| リネーム欄を畳む | 3（一覧クリック・パレット Enter・`Cmd+N`） | `open_note()` |
| undo 履歴を捨てる | 4（起動・セットアップ完了・切替・削除） | `replace_content()` |
| 派生状態の更新 | `notes` を変える全操作 | `refresh_derived()` |
| エディタ破棄の許可 | 5（切替・新規・リネーム・削除・終了） | `PendingAction` + `finish_save` |

**教訓の一般化の粒度にも罠がある。** 前身は「dot 始まりのリネームを拒否」で穴を塞いでいたが、
`load_dir()` が `.md` しか拾わない以上、**拡張子落ちもまったく同じ理由で一覧から消える**。
正しい一般形は「dot を拒否する」ではなく **「一覧から消える名前を作らせない」**で、
そう言い直して初めて穴が全部見えた（[ADR-0006](decisions/0006-rename-and-delete.md)）。

移植では、**前身が塞いだ穴そのものより「同じ理由で開く別の穴」を探すほうが効く。**

### 次に問うこと

- この性質を持つ経路を列挙できるか。**数はいくつか**
- 経路を**足す人**が同じ穴を開けない構造になっているか（合流点はあるか）
- この教訓は、症状の言葉ではなく**原因の言葉**で一般化できているか

## 第 3 章 失敗は沈黙してやってくる

**例外もログも出ないまま壊れる層がある。そこでは「効いている」ことを別の観察で確かめるしかない。**

### 実際に起きたこと — フォント三部作

| 段階 | 何をしたか | 何が起きたか |
|---|---|---|
| 1 | `Font::MONOSPACE`（総称ファミリ） | cosmic-text が漢字に `GB18030 Bitmap` を選び、Swash がラスタライズに失敗 → **グリフを黙って捨てる**。カナと英数は別フォントなので無傷 ＝ **漢字だけ消える** |
| 2 | `Font::with_name("Osaka-Mono")` で名指し | `"Osaka-Mono"` は PostScript 名。fontdb が照合するのはファミリ名 → **一度も解決されていなかった**。しかし失敗しても既定に落ちるので漢字は綺麗に出る |
| 3 | 見出しに `Hiragino Mincho ProN` | cosmic-text は **weight 完全一致の face しか採らない**。W3/W6 しか無いのに `Normal`（400）で要求 → **フォントが入っているのにゴシックへ落ちる** |
| 4 | 決着: `BIZ UDGothic` | 判定を目視から `name` / `hmtx` / `OS/2` テーブルの数字に変えた。ASCII 1024 : CJK 2048 を実測（[ADR-0013](decisions/0013-editor-font-biz-udgothic.md)） |

**この章の核心は段 2 にある。** 「漢字が出ている」ことを等幅が効いている証拠として使っていた。
主張（等幅である）と、それを確かめている観察（漢字が出る）が**対応していなかった**。
効いているかは**桁が揃うかでしか分からない**。

### 実際に起きたこと — 原理的に到達しないコード

| 何 | なぜ到達しないか |
|---|---|
| 未保存マーカーの点灯 | 判定が `if should_save {} else if marker {}` の排他で、`DIRTY_MARKER_DELAY(3000ms) > AUTOSAVE_MAX_WAIT(2500ms)` である以上 marker の条件が真なら save も必ず真。**「異常のシグナル」が異常時にこそ点かない** |
| `fuzzy::is_word_boundary` の camelCase 判定 | `lower()` を通したあとの文字を渡していたので `cur.is_uppercase()` は原理的に false。**判定に要る情報を、判定の前に潰していた** |
| `Ctrl+K` の `Sequence[Select(End), Cut]` | `Select` は publish するだけで `Content` は変わらず、`Cut` はその場で `selection()` を読むので常に空。**「空選択なら安全」という安全装置が常時作動していた**（[ADR-0016](decisions/0016-macos-control-key-bindings.md)） |

### 一般形

**「安全装置が効いた」と「安全装置が常時作動していた」は同じ見た目をする。**
no-op を安全策として選ぶなら、**動くはずの場合に動くことを別途固定する**必要がある。

そして沈黙する層では、**レンダリング結果より手前のデータで判定するほうが速くて確実**だった。
画面を見て「等幅っぽい」を判定するより `hmtx` の advance を 7 文字分並べるほうが速く、
候補 4 ファミリの可否が 1 コマンドで割れた。

### 次に問うこと

- これが「効いていない」とき、画面・ログ・例外に何が出るか。**何も出ないなら何を見れば分かるか**
- その観察は主張と 1 対 1 で対応しているか（**漢字が出る ≠ 等幅**）
- レンダリング結果ではなく、その手前のデータ（テーブル・数値・バイト列）で判定できないか
- この分岐は、**原理的に到達しうる**か（定数の大小・正規化の順序で潰れていないか）

## 第 4 章 テストは形ではなく効果で見る。そして届かない層を知る

### 実際に起きたこと — 空回りしたテスト 3 種

| 種類 | 何が起きたか |
|---|---|
| **形のテスト** | `Ctrl+K` を `matches!(steps, [Select(End), Cut])` で検査して満足した。**形は正しいまま効果だけが出ていなかった**（実機では選択されるだけ）。`content.text()` を突き合わせていれば 1 巡目で落ちていた |
| **前提が崩れた空回り** | `flush_saves` は `saving` が `Some` のときしか動かない。打鍵しただけでは保存が始まらないので「書いていないので当然通る」テストになった。対処は**前提そのものを assert する**（「ディスクに X がある」「`selected` が動いている」を先に確かめる） |
| **型による空回り** | `()` も `text::Renderer` を実装しているので、型注釈が無いと推論が `()` に決まり、**何も検証しないテスト**ができあがる |

### 実際に起きたこと — 効いたテストの型

- **失敗系は失敗させないと検証できない。** `chmod 0555` / `0000` で本物の権限エラーを起こし、
  切替が中断され本文がエディタに残ることを確認した
- **負のコントロール。** 修正を外して落ちることを見る。誤リネームの回帰 3 本、undo の履歴破棄、
  `Ctrl+K`、CRLF 対応のいずれも「**通ることではなく、外すと落ちることを見た**」
- **両方の入力で固定する。** `Ctrl+A` の `text` が制御文字のとき（macOS 実機）と `None` のとき。
  片方だけだと「テストは通るのに実機で効かない」実装が通る

### 実際に起きたこと — テストが届かなかった層

**最後のブロッカーは、テストの外側にあった。**
`Cmd+Q` は保存ガードを素通りして編集を消していた。テストが固定できるのは `CloseRequested`
**以降**だけで、**OS がそれを届けるかどうか**は見ていなかった。winit の macOS 実装では Quit は
`terminate:` セレクタで NSApp を直接終了させ、`CloseRequested` は発生しない
（[公開可否レビュー B-1](review-2026-08-17-public-release.md)）。
修正は [ADR-0021](decisions/0021-quit-through-close-guard.md)（Quit 項目の飛び先を
`performClose:` へ付け替え）。**塞いだのは実機ドライバで、ユニットテストではない。**

**そして「実機で確かめた」だけでも足りなかった。** 受け入れ条件を「終了 + ノートが 2 bytes」と
書いたが、終了が遅ければ自動保存が同じ 2 bytes を残す — **素通りのままでも条件を満たせる**。
終了までの経過時間を測って初めて、書いた主体を分離できた。
**観測値に到達する経路が 1 本だけか**を、条件を書く時点で確かめる。

静的検査にも同じ穴がある。`tags` は正しくパースされ **UI から一度も読まれていなかった**が、
`Note` が `pub` 公開型なので未使用フィールドは dead_code 警告の対象外で、`clippy` は黙っていた。

### 次に問うこと

- このテストは、**実装を壊したら落ちるか**（外して確かめたか）
- 検証しているのは「形」か「効果」か
- **前提（そこまで到達していること）を assert しているか**
- テストが固定できる範囲の**外側はどこか**。そこは誰が見るのか（実機・OS・依存ライブラリ）
- 合格の観測値に、**修正されていなくても到達できる別経路**は無いか

## 第 5 章 数字で決める — 計器・予算・最適化の順序

### 実際に起きたこと

**計器を常設した。** `view()` の構築時間を画面のステータス行に出した。
前身の落とし穴（`render()` にタグ集計を置いて打鍵ごとに全ノート走査）は、
**数字が見えていれば書いた瞬間に気づけた性質**のものだった。

**予算を持たない層が残っていた。** `view()` の 1ms は最初からあったが、
`update()` 側の予算は**このリポジトリに存在しなかった**。本文検索を入れて初めて
「打鍵 1 回の `refilter` が 20ms」が見えた（[ADR-0018](decisions/0018-palette-searches-note-bodies.md)）。

**最適化ラダー（20.3ms → 7.1ms）:**

| 段 | 変更 | 最悪ケースの平均 |
|---|---|---|
| 0 | 素朴な実装 | 20.3ms |
| 1 | `lower()` で ASCII を早期 return | 17.2ms |
| 2 | `lower()` でかな・漢字を早期 return | 12.5ms |
| 3 | **走査を 1 パスに**（開始位置ごとにスライスを切り直すのをやめた） | 7.8ms |
| 4 | `Peekable` をやめて生の `CharIndices` + `can_voice()` | **7.1ms** |

- **一番効いた段 3 は、アルゴリズムではなく実装の粗さだった。** 開始位置を 1 文字ずらすたびに
  スライスを作ってイテレータを初期化していた
- 「Unicode テーブル参照が重いはず」と当たりを付けた段 1・2 の効きは、段 3 の半分
- 効かなかった変更もある（`peek()` の絞り込みは 7.77 → 7.83ms で誤差）
- 結論: **当たりを付けた場所が外れることのほうが多い**

**予算は平均で定義した。** 最悪値は 7.3〜10.2ms とばらつく（他プロセス・サーマル）。
打鍵のたびに走るものの体感を決めるのは**連続した打鍵の均し**であって 1 回の外れ値ではない。

**最悪ケースの選び方も判断だった。** 「どこにも当たらないクエリ」＝打鍵途中の未完成語＝
**実使用で最も頻度が高い**。

**同じコードが違う数字を出したら、まず計測環境を疑う。** vault 読み込みが 185ms と出て焦ったが、
ディスクキャッシュが冷えていただけだった（暖機後 33ms）。移植検証でも同じ現象を踏んでいて、そのまま再演した。

**先回りで最適化しない。** まだ使っていない最適化段（先頭文字の逆像・増分絞り込み）は
**ADR に「使っていない段」として書いてコードには入れなかった**。RSS 164MB も実測してから決め、
仮想リストは不要と分かった。

### 一般形 — 数字は賞味期限を背負う

公開可否レビューが指摘したのはここだった。`implementation-notes.md` の「84 passed」は実際 145、
`CLAUDE.md` が指す実データ vault は本機にもう存在せず、**Done の定義の再現手段が消えていた**。
数字を書いたら、その数字が古びたことを誰がいつ気づくかまで決める。

### 次に問うこと

- この操作の**予算はいくつか**。誰が測るか。常設の計器はあるか
- 最悪ケースは**実使用の頻度**と一致しているか
- 測る前に最適化していないか。**効かなかった変更も記録したか**
- この数字は、いつ・何によって嘘になるか

## 第 6 章 記録の複利 — ADR が後から効いた瞬間

**ADR の価値は「決めたことを残す」より「決めなかったことを、理由ごと残す」にある。**

### 実際に起きたこと

| # | 何が起きたか | 出典 |
|---|---|---|
| 1 | **却下理由が後で検証された。** ADR-0006 は「削除の前に保存する」を「保存に失敗したら削除できなくなるほうが困る」で却下していた。突き合わせたら `.trash` への退避は同一ディレクトリの rename なので、**保存が失敗する状況では削除もどのみち失敗する** → 却下理由が成立しない | [ADR-0007](decisions/0007-closing-and-durability.md) |
| 2 | **却下が反転した。** 非同期保存は「本筋の解だが今回は大きすぎる」で却下されていた。変わったのは実装ではなく**判定基準**（公開するかどうか）。理由が書いてあったので**文脈の再構成なしに実装へ入れた** | [ADR-0014](decisions/0014-async-save.md) |
| 3 | **申し送りが次の周回で high に育った。** 2026-08-11 のレビューが出した high 3 件は、**全部「前の周回で自分が見送ると書いた場所」**だった | implementation-notes |
| 4 | **継承した判断の根拠が消えていた。** 前身の chrono 採用理由「依存に既に入っているので追加ダウンロードは発生しない」は iced では嘘。**コメントに理由が書いてあったから気づけた**（理由の無いコードなら依存だけ増やしていた） | [ADR-0005](decisions/0005-chrono-for-note-names.md) |
| 5 | **制約の成立条件を書いておいたので、例外を安全に見分けられた。** ADR-0004 の「トグルは成立しない」は普遍ではなく**フォーカス中の入力欄が存在するとき**の制約だった。プレビューは押した瞬間に漏れ先が画面から消えるので、例外にできた | [ADR-0019](decisions/0019-markdown-preview.md) |

### 一般形

却下理由は**将来検証できる仮説**として書く。「重い」「大きすぎる」だけでは検証できないが、
「`save_now()` の戻り値 `bool` が同期であることに全ガードが乗っているため」なら、
後からその前提が変わったかを確かめられる。実際 2 と 3 はそれで動いた。

そして**判定基準が変われば同じ事実から逆の結論が出る**。ADR-0012 → ADR-0014 の反転は、
新しい情報が来たのではなく「公開する」という軸が増えただけだった。

### 次に問うこと

- 却下したものを、**理由ごと**書いたか
- その理由は**将来検証できる形**か（「重い」ではなく「◯◯が◯◯に乗っているため」）
- 制約を書くとき、**成立条件**も書いたか
- 前の周回の申し送りを、次の周回の**最初に**読んだか

## 第 7 章 非目標は理由で書く。そして理由が嘘になる日が来る

### 実際に起きたこと

**非目標の理由付けが、存在しない代替手段を前提にしていた。**
spec の非目標にはこうあった:

> **全文検索**（SQLite FTS5 / tantivy）。約 1200 件を 30ms で読めているので、**当面は素の走査で足りる**

却下しているのは**インデックス方式**であって本文検索そのものではない。にもかかわらず、
その「素の走査」が実装されていなかった。全ノートの `raw` は起動時からメモリにあるのに、
`refilter` は `title` しか見ていなかった。公開可否レビューはここを
**「他人が最初に詰まるのは確実にここ」**と判定した（[ADR-0018](decisions/0018-palette-searches-note-bodies.md)）。

**非目標の「本質」を切り分けたら、要求と衝突しなくなった。**
「WYSIWYG 編集・プレビュー分割ペイン」の本質は**「編集を WYSIWYG にしない」**であって
「読むための表示を持たない」ではなかった。切り分けた結果、置き換え型プレビューは
非目標を壊さずに入った（[ADR-0019](decisions/0019-markdown-preview.md)）。

**仕様に書いてあることは実装の証明ではない。**
Boostnote 比較調査は「spec 上の扱い」と「実装確認済み状態」を**意図的に別の列に分けた**。
結果、タグ絞り込みが「非目標欄では絞り込みを前提に書かれているのに、機能テーブルに行が無く、
実装も存在しない」＝ **仕様側でも宙に浮いている**ことが見えた
（[Boostnote 比較調査](research-2026-08-15-boostnote-legacy-comparison.md)）。

### 一般形

非目標は「作らないもの」のリストではなく、**「なぜ今それが要らないか」の仮説の集合**。
仮説である以上、前提が崩れれば非目標も崩れる。

**理由の形で書いてあると、崩れたことに気づける。**
「全文検索は作らない」だけなら食い違いは見えなかった。
「素の走査で足りるから作らない」と書いてあったから、素の走査が無いことが矛盾として見えた。

### 次に問うこと

- この非目標の理由は、**実装済みの何か**を前提にしていないか。その前提は本当に存在するか
- 非目標の**本質**は何か。それを守ったまま要求を満たす形はないか
- spec に書いた各行に対応する `Message` / 関数 / テストは**実在するか**
- 実装が仕様とずれたら、**実装ではなく仕様を先に直す**か、ずれを ADR にしたか

## 第 8 章 設計は制約から降りてくる

### 実際に起きたこと

**フレームワークの制約が、機能の設計そのものを変えた。**
subscription はイベントを**観測できるが消費できない**。だから `Cmd+P` のトグルは成立せず、
閉じ方を Escape / ✕ / 背景クリックに寄せた。結論は
「**同じ操作を移植する**のではなく**同じ目的を、この土俵で成立する形に置き直す**」
（[ADR-0004](decisions/0004-palette-close.md)）。

**OS の権限の仕組みが、UI の形を決めた。**
「フォルダ選択ダイアログを出すか」は使いやすさの問題だと思って比較を始めたが、
実際には macOS の TCC から**ファイルを読む権利を受け取れる唯一の経路**（Powerbox）を選んでいた。
**UI の選択肢として並べている間は、どちらも「やり方が違うだけ」に見えていた**
（[ADR-0015](decisions/0015-vault-location-setup.md)）。

**依存の既定に手を出す範囲を最小にした。**
Control 系キーバインドの自前の表は、既定（`Binding::from_key_press`）**より後ろ**に置いた。
先に自前を引くと、既定が正しく処理している組み合わせを奪う。この順序にしたことで
**上流が直ったら自前の分岐は自然に到達不能になり、挙動は変わらない**
（[ADR-0016](decisions/0016-macos-control-key-bindings.md)）。fork / patch は
「直すのは 1 行だが、依存を自前管理へ引き上げるコストが釣り合わない」で却下した。

**境界の主張は、跨いで初めて実証された。**
`vault.rs` / `fuzzy.rs` は std のみ依存で UI 層への参照がゼロ。gpui → iced へ
**1 バイトも変えずに**動いた。「UI 層への参照ゼロ」という設計の主張が、
フレームワークを跨いだ実物で裏付けられた。

**非同期化の本体は、スレッドを変えることではなかった。**
`save_now() -> bool` の `bool` は、実は「**エディタの内容を破棄してよいか**」という**許可**を運んでいた。
スレッドの話だと思って着手すると、この許可の行き先を決め忘れてデータ喪失の穴が開く
（[ADR-0014](decisions/0014-async-save.md)）。

### 一般形

制約に出会ったら、**それが普遍か条件つきか**を先に決める。
条件つきなら条件を書く（第 6 章の 5）。普遍なら設計の前提に格上げする。

そして「選択肢が並んでいる」と感じたときほど、**実は選んでいるのが別の軸**であることを疑う。
UI の見た目を選んでいるつもりで権限の受け取り方を選んでいたのが ADR-0015 だった。

### 次に問うこと

- この制約は普遍か、条件つきか。**条件を書けるか**
- この UI の選択肢は、実は**権限・能力を受け取る手続き**の選択ではないか
- 依存の既定を上書きするとき、**上流が直ったら**自分のコードはどうなるか
- 同期の戻り値は何を運んでいるか。**値か、許可か**

## 終章 次のプロジェクトへ持っていくもの

### A. 着手前（設計）

- [ ] 守る対象と、**守り方が失敗したときの経路**を両方書く（第 1 章）
- [ ] その性質が通る**経路を列挙し、合流点を決める**（第 2 章）
- [ ] 非目標は**理由の形**で書き、理由が前提にしている実装が実在するか確かめる（第 7 章）
- [ ] **予算（数字）と計器の置き場所**を決める（第 5 章）
- [ ] 制約は**成立条件つき**で記録する（第 6・8 章）
- [ ] 未知は推測で埋めず、**安く実測できるならそちらを選ぶ**（移植検証があったので blind spot pass を省略した判断がこれ）

### B. 実装中

- [ ] 効いていることを、**主張と対応する観察**で確かめる（漢字が出る ≠ 等幅。第 3 章）
- [ ] テストは形ではなく**効果**。**外して落ちるのを見る**（第 4 章）
- [ ] 失敗系は**本当に失敗させる**（権限を落とす・容量を埋める）
- [ ] **測ってから最適化する。効かなかった変更も記録する**（第 5 章）
- [ ] 見送ったものは**理由ごと** Deviations へ。次の周回でそこが high になる（第 6 章）
- [ ] 変更は小さく、理由は 1 つ。**別の穴を同じコミットに混ぜない**（⌘ 混入とリネーム欄の排他を分けた判断）

### C. レビュー前・公開前

- [ ] **テストが固定できる範囲の外側**を列挙する（OS・依存・実機。第 4 章）
- [ ] **前の周回の申し送りを最初に読む**（第 6 章）
- [ ] **主張と実測を 1 行ずつ照合する表**を作る（3 回のレビューがすべてこの形式だった）
- [ ] docs の**数字の賞味期限**を確認する（第 5 章）
- [ ] 「本物だが不採用」を維持するなら、**前提と再導入条件**を書く（ADR-0007 の 3 条件）
